# 05 — 项目复盘：从“模型回答正确”到“系统判断可信”

> **项目：** 企业知识问答 Agent（第 3 题）  
> **证据口径：** V2/V3 各六组 `deepseek-flash` 真实运行 Trace，V3 45 项本地单元测试通过；另有两组真实正文变异对照。  
> **复盘重点：** 决策边界、检索相关性、冲突判定、引文完整性、故障恢复及可验证性。

## 1. 最初的目标与架构取舍

这次我刻意没有把之前 Deep Research Agent 的多 Agent、长期记忆和复杂部署方式全部搬进来。第 3 题真正要求证明的是：模型能根据工具返回的信息选择下一步，证据不足时不编造，冲突时不武断，并留下可供评审复核的实际执行过程。

因此项目最终采用**一个 DeepSeek 模型 + 两个本地业务工具 + 确定性验证器**：

- 模型决定何时搜索、读取哪份文档、继续检索还是结束。
- `search_documents` 负责候选召回；`read_document` 返回带 ID 与版本的原文片段。
- Python Controller 负责工具参数、错误、执行次数上限和日志；引用校验器负责阻止无依据的 `completed`。

这个取舍的关键不是“代码少”，而是把**不确定的业务行动**留给模型，把**确定的约束条件**留给代码。这样既能展示真实 ReAct，又便于构造可复现的验收案例。实现过程使用了 AI 辅助生成代码和评审建议；我的关注点是用真实输出判断该架构能否成立。

## 2. 最有价值的一次失败：正确答案被错误校验拦截

### 现象

第一次对“年假申请需要提前几天？”运行真实 DeepSeek 时：

1. 模型正确调用 `search_documents`，随后读取 D03。
2. D03:p1 明确写着“员工申请年假应至少提前3个工作日提交审批”。
3. 模型已生成带正确引文的回答，但程序最终输出了 `incomplete`，误报报销制度冲突。

Trace 还显示了额外的搜索和 D01/D02/D04 读取。也就是说，问题不是模型不知道答案，而是**系统把无关风险反馈给模型，诱导了无必要的继续执行**。

### 根因与修复

经过结合 Trace 的排查，并在 AI 协助下修改代码，定位到两层问题：

- **检索层：** 字符重叠匹配把低相关的报销制度排进了年假结果。
- **校验层：** 验证器按“本轮搜索命中过哪些文档”全局判断冲突，而不是先问“这些冲突是否属于当前问题”。

修复采用三类措施：过滤弱相关搜索候选；把冲突校验约束到当前问题主题；在 Prompt 中明确“问题已有直接证据时，不要想象无关的缺口”。同时增加数字与单位校验，防止把“工作日”和“自然日”混淆。

### 复测和对照

| 指标 | 首次实际运行 | 修复后实际运行 |
| --- | --- | --- |
| 状态 | `incomplete`（错误） | `completed` |
| 工具路径 | 多次搜索，读入无关文档 | 搜索 D03 → 读取 D03 → 结束 |
| 模型调用 | 7 | 3 |
| 工具调用 | 7 | 2 |
| Token | 14,965 | 3,667 |

本例中 Token 下降约 **75.5%**。这不是多次重复实验的平均提升，而是两次真实日志的直接比较。相比成本下降，更重要的是校验器不再把无关制度当成当前制度的冲突。

**我的核心收获：** Agent 可靠性不是靠“加上一个验证器”就自然提高。验证器的规则如果缺乏问题相关性，也会制造错误反馈；安全约束必须有明确的适用边界。

## 3. 冲突处理：新版本不自动意味着优先级更高

报销测试中，D01 规定 30 个自然日，D02 规定 15 个自然日。尽管 D02 版本日期较新，两份文档都没有说明覆盖关系、适用范围或优先级。

真实 DeepSeek 搜索到双方后，选择读取 D01 和 D02 的原文，最终返回 `needs_clarification`，提供双方引用并要求确认适用制度。

这里我认为最关键的工程判断是：**“找到了较新文档”和“有权认定它替代旧制度”不是同一件事。** 没有优先级证据时，保留冲突比猜测一个确定答案更符合企业知识问答的可靠性要求。

## 4. 无资料与工具故障：两种不同的不确定性

### 资料外问题

关于“宠物托管补贴”的查询，第一次搜索没有返回可用文档。真实模型随后主动改写关键词，再进行两次搜索；虽然补查结果出现了报销文档，但它识别出这些资料不能支持宠物托管补贴结论，因此输出 `insufficient_evidence`。

这说明“检索到一些文档”不等于“证据足以回答”。严谨的表述应是**当前知识库没有足够依据**，不能推断现实中绝对不存在这项制度。

### 工具故障

故障测试人为让第一次 `search_documents` 返回 `TOOL_TEMPORARY_FAILURE`。Python 工具层并未自动替模型决定重试；DeepSeek 观察错误后自行重新调用搜索，再读取 D04 并生成带引用的密码重置答案，最终 `completed`。

我把它作为**模型处理本地业务工具错误**的证据，而不是“真实 DeepSeek API 曾宕机后恢复”的证据。这一区分对评估可靠性很重要。

## 5. 上下文追问：通过了验收，但还存在效率空间

测试问题“那由谁来审批？”依赖前面的年假申请对话。模型能够从历史中还原问题主题，并检索到 D03:p2“年假申请由员工的直属主管审批”。

不过首次生成最终回答时，模型同时提到了“提前 3 个工作日”，却没有为这个额外数字事实附上 D03:p1 引文。校验器反馈 `unsupported_numeric_claims:3工作日`，模型又读取了一次 D03，补齐 p1 引用后返回 `completed`。

这组真实记录是一个典型的**正确性优先与成本之间的权衡**：验证器保证了附带事实有依据，但也让模型重复读取已见过的文档。后续可以约束回答只聚焦当前追问，或者让验证器更清晰地提示已有证据缺口，使模型在不牺牲引用可靠性的情况下减少重复调用。优化仍须保留模型对下一业务行动的决定权。

## 6. 我如何判断项目“通过”，而不只看最终状态

本项目把验收拆成三层：

| 层次 | 检查内容 | 已有证据 |
| --- | --- | --- |
| 工程正确性 | 工具参数、引用匹配、冲突保护、故障注入、调用上限 | 开发阶段 26 项本地单元测试通过 |
| 真实模型行为 | 模型根据观察结果继续检索、读取、结束或澄清 | 六组 `mode=live_deepseek` 的真实 Trace |
| 业务结果 | 明确答案有引文；冲突不选边；资料外不编造；故障可恢复或说明限制 | 六种考题场景的实际输出和评估材料 |

六组真实测试累计 **21 次模型调用、16 次工具调用、27,965 Token**。其中正常、冲突、资料外、改写、追问和工具失败六种场景达到各自主要验收预期。Trace 和证据位于 `examples/live/`，详细表格位于 `docs/03-evaluation.md`。

但单次通过不等于稳定性达标；本次没有完成大规模随机改写、长期运行或生产数据测试。

## 7. 仍存在的局限与下一轮优先级

**优先级一：知识库相关性与制度适用关系。** 当前字符级检索适合小规模合成数据；新的相关性阈值虽能过滤本次噪声，也可能漏掉弱词面匹配的正确文档。后续应通过改写语料衡量召回与精确率，并显式建模适用部门、生效日期、替代关系、优先级，再进行冲突判定。

**优先级二：更强的证据支持检查。** 现有守卫能校验引文来自已读原文，检查部分数值及单位，但仍不能保证任意自然语言断言都被引文逻辑蕴含。可增加断言拆分、证据对齐与独立评估；同时避免把“信息未出现”当成“事实不存在”。

**优先级三：多轮成本与稳定性。** 优化追问时的引用覆盖和缓存利用，避免重复读文档；再对每类场景多次运行，记录通过率、平均调用次数、Token 成本及失败分布，而不是只保留一次成功样例。

**明确未做：** 真实企业知识库接入、生产级权限控制、向量/混合检索部署、线上服务、长期稳定性压测。这些不属于本次最小可交付范围，不应包装成已经具备的功能。

## 8. 个人复盘：我真正获得了什么

这个项目中，AI 参与了代码草案、方案建议、调试分析和文档组织；我没有把它们包装成独立手写成果。我的实际工作集中在确定适合已有经验的选题、采用可复现的交付范围、配置并运行真实 DeepSeek、保留第一次失败、使用修复版复测、收集六组 Trace，并将是否达标建立在可验证的行为而非模型自述上。

如果用一句话总结这次经验：

> **Agent 开发的难点不是让模型“调用一次工具”，而是确保工具给出的观察、程序添加的约束以及最终答案之间始终保持一致。**

这也是我后续做 Agent 工程时会优先关注的部分：先定义成功与失败证据，再决定需要多少模型、工具和基础设施。

## 9. 后续代码审查：元数据陈旧与真实引用的语义风险（V3）

在六组真实模型场景已经通过后，进一步对照考题的审核要点发现两个潜在缺陷：

1. 旧版冲突判断依赖合成知识库中的固定 `fact_value`，如果仅修改 D02 原文，不同步修改该字段，就可能出现“正文规定一致，系统却仍判冲突”的状态错配。
2. 旧版校验器能确认引用来自真实段落，但对于“年假不需要审批”“支持离线编辑”这类明显与原文相反的断言，单纯字面引文检查无法保证答案正确。

AI 协作中采用的修复方式是：**以当前原文作为冲突事实的唯一来源**，把静态元数据降级为主题分组；再增加针对审批必要性、审批人、产品能力极性的有限事实检查。为避免过度包装，不把这些规则称作通用自然语言蕴含系统。

此外，把文档读取拆成支持可选 `paragraph_id` 的精确读取，同时保留整篇短文档的默认行为，既能回应题目的“片段读取”要求，也避免破坏已有案例的使用方式。

新的单元测试达到 **45 项通过**，离线正文变异确认了 D02 15→30 自然日后不再报告原期限冲突。之后已实际执行真实 DeepSeek 正文变异 A/B：报销冲突原始状态为 `needs_clarification`，修改后为 `completed`；年假 D03 3→5 工作日修改后的第一次运行遭遇 APIConnectionError，保留失败记录并单独重试，补测为 `completed` 且引用新的 5 工作日原文。原始失败的 `summary.json` 保持不变，成功重试另有独立文件。

已完成变异真实调用及六类 V3 回归，接下来优先冻结提交版本，核对文档和 Trace 的版本一致性、Git 忽略密钥规则、最终仓库 URL 与 Commit SHA；今后可针对语义校验的误报及额外调用开展效率优化。

## 10. V3 真实回归结果与新的取舍（2026-10-30）

V3 六类验收均有真实 `deepseek-flash` Trace，22 次模型调用、19 次工具调用、34,766 Token。六组主要业务目标通过；10 条最终引文均能与同次成功读取的原文对应。

此次对我最有价值的发现，并非“所有成本都下降了”，而是**守卫更严格后，模型有时需要多做一轮工作才能给出可验证的回答**：

- 报销冲突案例初次完成时用“30天/15天”概述原文的“自然日”，触发数字单位保护；模型再读取两份文档全文，最终保留双方原文与澄清请求。
- 改写问答案例最初引用年假期限段落，却附带提及审批人；源证据检查反馈缺少审批人段落，模型再次按段落读取并补全引用。
- 上下文追问本轮使用 `paragraph_id=p2` 直接读取审批人条款，未发生多余的补证循环。

另一项风险是**外部网络故障与模型推理失败必须分开**：年假正文变异首次受到 `APIConnectionError` 阻断，这一轮根本没有成功进入检索流程；单独重新执行相同修改版数据后正常完成，因此应记为“首次连接失败、独立复测通过”，而不是“首次即通过”。

我倾向于保留目前对明确数字单位和来源支持性的保守校验，而不是为减少 Token 直接放开；更合理的下一步是针对模型表达与工具层证据范围设计更准确的提示，并做多次测试验证成本与误报率。

**未解决的能力边界：** 正文事实抽取针对当前合成报销语料；`evidence.py` 只拦截部分显式否定、审批人和功能支持反转；一次通过仍无法证明真实企业知识库上的长期可靠性。

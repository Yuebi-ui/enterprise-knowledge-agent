# 03 — 评估报告：V3 真实 DeepSeek 验收与文档变异对照

> **实验对象**：企业知识问答 Agent（题目 3）  
> **模型**：真实 DeepSeek API / `deepseek-flash`  
> **业务数据**：六份合成企业文档，不代表真实公司制度  
> **本次评估时间**：2026-10-30  
> **证据路径**：`examples/live_v3/`、`examples/live_mutation_v3/`；历史 V2 证据在 `examples/live/`

## 1. 总结：三类验证分别是什么

- **V3 本地单元测试**：45 项 `unittest` 通过，覆盖基础工具、状态、冲突、文档变异、精确段落读取和有限语义反例。测试实际执行的是 Python 逻辑，不是模型行为。
- **V3 六组真实模型回归**：六组状态满足各自的主要验收目标；真实运行共 **22 次模型调用、19 次工具调用、34,766 Token**。
- **真实模型文档变异对照**：D03 年假期限 3→5 工作日，修改后的首轮 API 连接失败，**独立重试成功**；D02 报销期限 15→30 自然日，使 D01/D02 原本存在的期限冲突解除，真实模型最终状态从 `needs_clarification` 变为 `completed`。

**上述三类结论证据不同，不互相替代。** 尤其不能把离线文档变异检查当作真实 DeepSeek 决策。

## 2. 六组真实模型验收结果

| 案例 | 最终状态 | 模型调用 | 工具调用 | Token | Trace 核查重点 |
| --- | --- | ---: | ---: | ---: | --- |
| `normal` | `completed` | 3 | 2 | 4,144 | D03:p1；年假至少提前3个工作日 |
| `conflict` | `needs_clarification` | 5 | 5 | 9,866 | 引用D01/D02；30与15自然日无法判定优先级；经历1次校验反馈 |
| `out_of_scope` | `insufficient_evidence` | 3 | 3 | 4,205 | 补充检索后仍无宠物托管补贴依据；不编造 |
| `paraphrase` | `completed` | 5 | 3 | 7,810 | D03:p1/p2；补齐审批人引用；经历1次校验反馈 |
| `follow_up` | `completed` | 3 | 2 | 4,174 | 从年假上下文定位 D03，按 paragraph_id=p2 精确读取直属主管 |
| `tool_failure` | `completed` | 3 | 4 | 4,567 | 第一次搜索被注入临时错误；另一搜索成功；后续再次检索并读取 D04 |

**合计：** 22 次模型调用、19 次工具调用、34,766 Token。

所有六组均能看到 `mode=live_deepseek` 和 `model_decision`／`tool_result` 事件；模型/工具调用数与 Trace 事件数一致。对其中的 **10 条非空引用**，逐条检查了文档 ID、段落 ID、版本日期及引文字符串，均能在**同次执行中成功的 `read_document` 原文**里找到对应内容。

`examples/live_v3/manifest.json` 的 `heuristic_passed=6/6` 是自动初筛；以上还包含了对真实答案和 Trace 的逐项核对，不能仅凭自动布尔值断言语义完全正确。

### 2.1 有明确答案：正常问答与改写

`normal` 通过 `search_documents` 得到 D03，随后执行 `read_document(D03)`，引用 D03:p1 给出“至少提前 3 个工作日”，状态 `completed`。

`paraphrase` 最初回答同时提及审批人但只引用 p1，验证器反馈 `unsupported_approval_actor`；真实模型随后额外读取 D03:p2，并补齐引文后 `completed`。这既是“修复反馈后重新决策”的证据，也说明更严格的引用要求会增加调用成本。

### 2.2 同主题文档冲突：不能擅自选择较新制度

`conflict` 搜索到 D01/D02，首先按 `paragraph_id=p1` 读取双方期限原文，发现 30 与 15 个自然日冲突。首次最终回答把原文“自然日”概括为“天”，触发数值与单位校验 `unsupported_numeric_claims:15天,30天`。模型据反馈再次读取 D01、D02 全文并更新引文，最终返回 `needs_clarification`，说明缺少适用范围及优先级，不武断以版本日期判定规则 B 优先。

**重要技术细节：** 这一次虽然通过，却消耗 5 次模型调用、5 次工具调用。`3个工作日` / `3天`、`30个自然日` / `30天` 的保守区别在制度问答中有意义，但进一步优化时可降低重复读取成本，不能为了少调用而放松冲突保护。

### 2.3 证据不足和上下文追问

`out_of_scope` 首次“宠物托管补贴”查询无结果，模型继续以不同关键词检索；虽偶然返回报销制度，但没有将其视为宠物政策依据，状态 `insufficient_evidence`，没有捏造金额或申请流程。“当前资料库未能找到”不等于现实中绝对不存在。

`follow_up` 根据对话历史理解“那由谁来审批？”是在问年假，搜索 D03 后精确调用 `read_document(doc_id="D03", paragraph_id="p2")`，引用直属主管条款，直接返回 `completed`，没有重复读取或校验反馈。

### 2.4 工具失败和模型行动

`tool_failure` 第一轮由真实 DeepSeek **一次发起两个搜索调用**。本地故障注入让其中第一次 `search_documents` 返回 `TOOL_TEMPORARY_FAILURE`；同轮第二次搜索已经成功得到 D04。模型看到故障与成功结果后，下一轮仍自主调用 `read_document(D04)`，并再次搜索相关问题，最终引用 D04:p1/p2 完成回答。

因此该例证明**真实模型能够观察到业务工具错误并继续采取动作**，但不能描述成“只有一个搜索调用失败后模型才首次重试”，也不是 DeepSeek API 故障恢复实验。

## 3. 高分审核重点：修改文档后，答案与行为是否同步变化？

实验代码：`scripts/run_live_mutation.py`。工具独立复制 `data/documents.json`，不直接覆盖正式知识库。

| 实验 | 原始真实模型运行 | 修改后真实模型运行 | 结论 |
| --- | --- | --- | --- |
| D03：3→5 个工作日 | `completed`，引用“3个工作日” | 首次 `APIConnectionError` / `tool_error`；单独补测为 `completed`，引用“5个工作日” | **经重试通过** |
| D02：15→30 个自然日 | D01=30、D02=15，`needs_clarification` | D01/D02 均为30，`completed`，引用双方原文，冲突清空 | **通过** |

**必须保留失败记录：** `examples/live_mutation_v3/summary.json` 仍然反映第一次完整运行中“年假修改后 API 连接失败”，所以原始 `all_pass=false` 并非文档变异逻辑不成立。成功补测原始记录另存于 `examples/live_mutation_v3/leave/modified_retry.json`；追加的审查说明在 `independent_review_after_retry.json`。绝不把第一次失败记录修改成成功。

两组对照展示了不同层面的“证据敏感性”：

- **事实值随原文改变**：年假 3→5 个工作日，检索和读取动作可以保持一致，但最终答案与引用需要更新。
- **最终状态随冲突事实改变**：报销 30 vs 15 变为 30 vs 30 后，最终从请求澄清转为确定回答。此前静态 `fact_value` 导致的陈旧冲突问题已通过正文抽取和回归测试处理。

## 4. 源引文可靠性和边界

`validation.py` 要求成功搜索、已经读取过的原文引文、匹配的版本和数字单位。V3 另外检查：

- 引用与当前明确查询的主题是否明显不相关；
- 审批是否必要的明确反向表述；
- 审批人与引文不一致；
- 产品“支持/不支持”极性反转；
- 本次文档原文是否真的仍存在 D01/D02 报销期限冲突。

本地单测覆盖了“真引文却得出反向结论”的若干反例。**这些是可测试的有限规则，不是通用自然语言推理（NLI）或完整事实一致性证明。** 复杂推论、资料权限和大规模召回均是未来工作。

## 6. 复现命令（Windows / VS Code）

```powershell
# 1. 全部本地代码测试
python -m unittest discover -s tests -v

# 2. 不用 DeepSeek Key 的正文变异自检
python -m scripts.run_live_mutation --scenario all --dry-run

# 3. V3 六组真实模型回归；输出不覆盖 V2 历史记录
python -m scripts.run_live_cases --out examples/live_v3

# 4. V3 真实模型正文变异对照；会调用模型产生费用
python -m scripts.run_live_mutation --scenario all
```

每次真实模型调用都有随机性或网络波动，失败时应保留真实 Trace 并追加重试记录。测试通过不代表生产环境稳定性，交付前还应检查 `.env`/密钥、GitHub 仓库访问权限及最终 Commit SHA。

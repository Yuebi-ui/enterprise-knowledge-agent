# 04 — AI 辅助开发记录与个人工程贡献

> **项目：** 企业知识问答 Agent（第 3 题）  
> **开发辅助：** ChatGPT（需求分析、代码初稿、方案建议、故障排查、测试与文档辅助）  
> **Agent 运行模型：** DeepSeek `deepseek-flash`（真实 API）  
> **验收证据：** `examples/live/`（V2 历史）、`examples/live_v3/`（V3 六组回归）及 `examples/live_mutation_v3/`（文档变异），并见 `docs/03-evaluation.md`  
> **记录原则：** 如实区分 AI 辅助生成的实现、我实际参与的技术选择与工程集成、以及真实模型验证结果。下文提到的代码调整为**AI 辅助起草、我采用并通过实测验证的项目修改**，不意味着我独立逐行手写了相关补丁。

## 1. 我的开发目标与 AI 使用方式

我此前有过 Deep Research Agent 的开发实践，了解检索、工具调用、证据核验和执行状态控制的基本问题。在这次限时笔试中，我希望把重点放在**能否构建一条可复现、可观察、可验收的 Agent 决策链路**，而不只是展示多 Agent 或复杂框架。

我采用 AI 辅助开发来提高方案梳理、编码和问题定位的效率，但评估一个改动是否有效，最终依赖三类证据：

1. **真实决策：** 模型是否根据工具返回的信息，自主决定继续搜索、读取、澄清还是结束，而不是由固定脚本代替决策。
2. **可靠引用：** 最终答案能否对应本次运行中真实读取的原文；相互冲突的制度是否被完整呈现。
3. **可验证结果：** 单元测试与真实 DeepSeek 调用分别留证，失败案例、修复前后差异和运行边界均可检查。

因此，AI 给出的代码和建议是开发输入；**我以题目约束、实际 Trace 和复测结果判断它是否适合保留**。

## 2. 技术方案中我重点确认的选择

| 决策点 | 项目采用的方案 | 判断依据 |
| --- | --- | --- |
| 选题 | 第 3 题：企业知识问答 Agent | 与我已有的检索及工具调用实践更接近，能围绕来源引用、冲突处理、资料不足及失败恢复设计明确的测试。AI 参与了选题比较，我确认采用该方向。 |
| Agent 架构 | 单 Agent + DeepSeek 原生 Tool Calling | 这道题的重点是“模型决策 → 执行工具 → 观察结果 → 再决策”，不必为了形式增加 Supervisor、Researcher 等多个角色。架构越精简，也越容易解释每一次模型决策。 |
| 工具设计 | `search_documents`、`read_document` 两个独立工具 | 搜索摘要只用来筛选候选文档；模型决定读取哪份文档后，才能获得可引用的原文。这使“检索”与“证据获取”的边界可观察。 |
| 数据设计 | 带 `doc_id`、段落、版本日期的六份合成制度与产品文档 | 用可控制的模拟数据稳定覆盖正常答案、同主题制度冲突及资料缺失，不声称这些内容来自真实企业。 |
| 守卫设计 | Python 做参数校验、原文引用核验、数字与单位约束、调用上限；DeepSeek 做业务决策 | 确定性约束适合放在代码层；“搜索哪个词、读取哪些文档、是否需要澄清”仍交给模型判断。 |
| 实际验证 | DeepSeek Live Trace + 本地单元测试 | 离线 ScriptedModel 可以测程序行为，但不能替代真实模型 ReAct 证据，因此需要独立运行 Live 场景。 |

我关注的不是“用了多少 AI 技术组件”，而是系统能否在出错时给出可追溯的原因、在证据不足时主动保留不确定性，并以较低成本完成考题要求。

## 3. 个人参与的修改与工程迭代（重点）

项目的首版代码由 AI 辅助生成。在拿到第一次真实 DeepSeek 运行结果后，我没有仅以“模型回答文字正确”作为验收依据，而是把**最终状态、工具返回和校验反馈**一起检查，并反馈异常日志，采用了针对性的修复方案。

以下是本次项目里实际落实的修改及其验证依据。**具体补丁由 AI 协助分析和编写，我负责将方案用于本地项目、运行真实模型并比较修改前后的结果。**

| 修改位置 | 初版暴露的问题 | 采用的修改 | 我关注的工程判断与验证 |
| --- | --- | --- | --- |
| `src/kb.py` | 年假查询除了 D03，还返回 D01、D02 等低相关报销文档。 | 增加弱匹配过滤和相对相关性门槛，降低噪声结果进入后续步骤的概率。 | 检索精确率不能只靠增加阈值；还要确保报销查询仍能同时召回 D01/D02，否则可能把真实冲突过滤掉。修复后正常案例只返回 D03，冲突案例仍返回 D01/D02。 |
| `src/validation.py` | 只要本轮检索过 D01/D02，就可能把它们之间的报销冲突误应用到年假问答。 | 冲突保护由“全局检索文档冲突”调整为“与当前问题主题相关的冲突”；同时强化引用和数值单位检查。 | 安全机制不能脱离问题语义。应保留真正的报销冲突保护，但不能否决已有 D03 原文支持的年假答案。 |
| `src/agent.py` | 旧校验流程缺少当前用户问题这一上下文，无法正确限定冲突适用范围。 | 调用最终答案校验器时传入当前问题，支持按问题主题约束冲突检查。 | 修复需要贯穿 Agent 调用入口与验证器，而不是只修改 Prompt 文案。 |
| `src/prompts.py` | 模型已经有完整原文证据时，仍可能写入假设性“特殊情形”等信息缺口，并继续检查无关文档。 | 明确相关文档范围，要求直接有证据的问题使用 `completed`，`missing_information=[]`，不凭空推测无关例外。 | Prompt 负责引导模型行为，程序守卫负责最终把关；不能只靠“提示模型小心”来保证正确性。 |
| `tests/test_core.py` | 原测试未覆盖“检索到无关冲突时，正常问题被误拦截”这一真实失败路径。 | 增加年假检索过滤、无关冲突不阻断、真实报销冲突仍受保护、数值单位错误及完成状态一致性等回归测试。 | 修复不能以牺牲原有冲突安全性为代价；正常和冲突案例必须同时验证，不能只重跑通过一个输入。 |

这组修改体现了我对两个不同问题的区分：

- **检索层的相关性问题：** 不应让大量无关结果消耗模型和工具调用成本。
- **验证层的适用范围问题：** 即使检索误召回了无关文档，也不应把其他主题的冲突当作当前问题的冲突。

因此，这次调整不是简单“放松校验让测试通过”，而是**收紧错误的触发条件，同时保留真正需要的冲突保护**。

### 修复前后的实测对照

首次问题：“年假申请需要提前几天？”

| 指标 | 修复前的真实运行 | 修复后的真实运行 |
| --- | ---: | ---: |
| 最终状态 | `incomplete` | `completed` |
| 模型调用次数 | 7 | 3 |
| 工具调用次数 | 7 | 2 |
| 总 Token | 14,965 | 3,667 |
| 检索与校验表现 | D03 答案正确，但被无关 D01/D02 冲突误拦截 | 检索到 D03，引用 D03:p1，`conflicts=[]` |

这两次实测的 Token 使用量相差约 **75.5%**。我把它作为**同一输入、两次实际运行的观察对比**，不将其包装成大规模性能基准或稳定的平均节省比例。

特别重要的是，我没有因为修复后的年假场景变成 `completed` 就停止验证，而是继续使用真实 DeepSeek 运行 D01/D02 的报销冲突问题。结果仍然是 `needs_clarification`，且引用双方原文，说明这次修复没有直接破坏最关键的冲突验收路径。

## 4. 我在本地实际完成的集成与验收工作

除了采用上述代码修改，我还完成了这些与模型输出无关、必须在真实环境中操作的工作：

1. **配置独立运行环境。** 在 Windows + VS Code 环境中处理 Conda 激活与 Python 解释器问题，安装项目依赖，保证 CLI 可以运行。
2. **接入真实模型。** 在本机通过 `.env` 配置 DeepSeek API Key、接口地址和模型名称；密钥与 `.env.example` 分离，避免把真实密钥提交到仓库。
3. **提供原始故障证据。** 首次 `normal` 运行返回 `incomplete` 后，保存完整 JSON 和 Trace，而不是只截取正确答案或忽略失败状态。
4. **应用修复并回归。** 将更新后的代码纳入现有项目，对相同输入重新调用 DeepSeek，再测试报销制度冲突，观察正确性、状态及工具调用差异。
5. **完成六组真实模型场景。** 运行正常问答、文档冲突、资料外问题、改写问题、上下文追问及工具失败，保存输出与 Trace 供复核。

这些工作并不意味着我独立编写了首版代码或全部补丁；它们体现的是**方案集成、真实运行、问题反馈、风险识别及验收判断**等工程参与。

## 5. V2 六组真实 DeepSeek 测试：我如何判断通过

以下为历史 V2 记录，使用 `mode=live_deepseek`，保存在 `examples/live/`。其中业务文档是模拟的，但**模型工具选择和后续决策来自真实 DeepSeek 调用**。

| 真实场景 | 最终状态 | 主要核验点 |
| --- | --- | --- |
| `normal` | `completed` | 搜索并读取 D03，引用 D03:p1；年假至少提前 3 个工作日。 |
| `conflict` | `needs_clarification` | 读取 D01/D02；分别保留 30 与 15 个自然日的规定，不能仅凭版本日期擅自选择。 |
| `out_of_scope` | `insufficient_evidence` | 找不到宠物托管补贴依据时继续补查，最终明确当前知识库证据不足，不编造政策。 |
| `paraphrase` | `completed` | 年假问题改写后仍找到相关制度并引用原文。 |
| `follow_up` | `completed` | 根据上文理解“那由谁审批”，引用直属主管审批条款；校验反馈后补充缺失引用。 |
| `tool_failure` | `completed` | 第一次本地搜索工具被注入模拟故障后，真实模型观察错误并自行重新检索，最终读取 D04。 |

六组真实运行记录合计 **21 次模型调用、16 次工具调用、27,965 Token**。六组均达到对应的主要验收目标；这只说明此次运行通过，不能断言所有随机输入都能稳定通过。

### 我认为比较有价值的两条不同决策路径

- **有充分证据时：** `search_documents` → `read_document(D03)` → `completed`。
- **制度存在无法判定的冲突时：** `search_documents` → `read_document(D01/D02)` → `needs_clarification`。

这两条路径在真实 Trace 中可观察，体现模型在接收不同工具结果后选择不同的最终行动，而不是固定脚本在所有问题上输出同一种结果。

## 6. AI 参与范围、验证边界与仍待改进之处

### AI 协助了什么

ChatGPT 参与了需求与选题比较、项目代码和文档初稿、测试设计、异常 Trace 解读、修复补丁生成，以及最终材料整理。首版核心代码和修复代码并非我全部独立手写；我不把 AI 的生成工作改写为个人独立编码成果。

### 我如何避免依赖 AI 的口头结论

- 不把“AI 说已经修好了”当成成功标准，而是运行同一真实输入并保存修复前后的完整记录。
- 不只检查最终答案，还检查 `model_decision`、`tool_result`、具体调用的文档和引用是否一致。
- 修复正常场景后再测试冲突场景，检查是否出现安全边界回退。
- 把本地 ScriptedModel / 单元测试与真实 DeepSeek Tool Calling 分开标注，不把模拟决策作为真实 ReAct 证据。
- 把人为注入的 `TOOL_TEMPORARY_FAILURE` 描述为**业务工具故障模拟**，而非真实 DeepSeek API 宕机。

开发环境中曾完成 **26 项本地单元测试**；正式提交前仍应在提交版本的本机环境中重新执行测试命令并核对结果，确保文件替换后没有引入遗漏。

### 我认为当前仍有三个边界

1. **轻量检索不是生产级企业搜索。** 阈值提高能减少本例误召回，但也可能造成召回不足。需要更多问题改写测试或混合检索对照来衡量。
2. **精确引用不等于完整语义核验。** 程序能检查来源、段落、版本、部分数值与单位，但不能证明任意回答句子都被引用严格蕴含。
3. **上下文追问存在重复读取。** `follow_up` 真实 Trace 中模型为了补齐数值引用再次读取 D03，虽然结果正确，但可以通过缩小回答范围或更清晰的反馈减少额外调用。

## 7. 小结：个人贡献的核心

本项目采用 AI 辅助开发，并非以“手工编写所有代码”作为个人贡献证明。对我来说，更关键的是：

**我确认了符合题目验收重点的技术范围，完成真实 DeepSeek 环境接入，发现并保留了首版系统的失败证据，采用与验证了检索、冲突守卫和 Prompt 的针对性修复，再通过六组真实 Tool Calling 运行判断系统是否满足核心需求。**

我从中得到的认识是：一个 Agent 的可靠性不仅取决于模型会不会调用工具，还取决于**检索结果是否相关、校验规则是否用在正确范围、反馈是否能帮助模型调整行为，以及整个过程能否被真实日志证明**。


## 8. V3 代码审查后的新增改动（AI 辅助实现，已进行真实复测）

为了进一步对照题目“替换文档内容，核对答案与动作是否改变”及“检查原文是否支持回答”的审核点，本轮在代码审查与 AI 协作中补充了两类工程改进。

**正文而非元数据作为事实来源：** 在 `src/kb.py` 中取消根据静态 `fact_value` 认定冲突，改成从当前文档段落中提取报销期限；当 D02 改为与 D01 相同的 30 个自然日时不再误报旧冲突。对此设计了“残留旧字段”“新期限冲突”“单位变化仍有冲突”等回归用例。

**引用不仅要真实，也要避免显式反向事实：** 新增 `src/evidence.py`，把审批必要性、审批人及“支持/不支持”做成有限范围的原文一致性检查；同时在 `src/tools.py` 中提供可选 `paragraph_id` 精确段落读取，并为合并多次部分读取增加单测。

这批修改由 AI 辅助设计和编码；随后我在自己的项目环境中执行了真实 DeepSeek 回归和正文变异对照，将结果与真实 Trace 一起保存。**45 项本地单元测试通过，V3 六组真实回归也达到主要验收目标；两组正文变异实验均获得真实模型支持的成功结果，其中年假实验需要在首次 API 连接失败后单独重试。**

这一轮最值得保留的技术判断，是不能为“容易得到确定答案”而弱化冲突保护：需要同时验证“原文相同则不应冲突”和“原文不同则必须保留冲突”，并区分代码级验证与真实模型决策。

## 9. V3 实际复测后的个人验收判断（2026-10-30）

采用 AI 辅助形成的 V3 改动后，我在本地重新运行了六类真实 DeepSeek 场景，并将原始结果存于 `examples/live_v3/`。六组验收状态均符合预期，共 **22 次模型调用、19 次工具调用、34,766 Token**；10 条最终引文可从同次 Trace 的 `read_document` 中核对。

在**文档替换实验**中，D03 年假期限从 3 工作日改为 5 工作日后，首次修改版调用遭遇 `APIConnectionError`，不能作为成功证据；之后我仅重新运行修改后的那一组，得到了引用新原文的 `completed`。D02 报销期限从 15 自然日改为 30 自然日后，模型从原来的 `needs_clarification` 转为 `completed`，没有继续依赖过期的冲突判断。

我对这次结果的判断重点是：**事实变更应改变事实性回答；冲突解除应改变最终任务状态。** 与此相对，工具调用顺序未必需要改变，不能把“调用序列相同”直接判断为 Agent 不够动态。

更严格的事实检查也带来代价：V3 冲突案例最初把“自然日”简写为“天”而触发校验反馈；改写案例首次提及审批人却未引用对应段落，触发另一轮反馈。两次均由真实模型继续补证而完成。这些 Trace 说明校验机制有效，但不证明系统整体 Token 成本降低。

**协作边界保持不变：** V3 代码草案和检查逻辑由 ChatGPT 辅助分析、编写；我在本机实际接入模型、运行故障与对照、提供错误输出、采用修复并验证其效果。面试中应能够解释静态 `fact_value` 为什么会陈旧、正文如何影响冲突判定，以及守卫为何仍不等于通用语义推理。
